# 提交规范的设计思想

> 个人知识库的提交规范，本质是**给自己留一个可回放的内容日志**：长期维护下，`git log` 就是内容演进的编年史。规范要足够轻，让"写提交"不成为负担，同时足够结构化，让历史可检索。

## 设计目标

1. **类型即索引**：提交信息首词是类型，`git log --oneline` 一眼区分"新内容 / 修复 / 重构 / 杂项"
2. **中文正文**：内容变更的描述用中文（本仓库内容本身以中文为主），与笔记语种一致
3. **单主题提交**：一次提交只做一件事，方便定位与回退

## 提交信息格式

```
<type>: <中文简述>
```

| type | 含义 | 示例 |
| :--- | :--- | :--- |
| `feat` | 新功能/新章节 | `feat: 新增 03-objects 章节内容` |
| `fix` | 修复 bug/渲染问题 | `fix(types): 安装 @types/node 并加入 tsconfig types 数组` |
| `docs` | 文档更新 | `docs: 更新 README 学习进度` |
| `refactor` | 重构，不改行为 | `refactor: 统一参考层速查格式` |
| `style` | 格式调整（不影响功能） | `style: 调整 .prettierrc` |
| `chore` | 杂项（依赖、配置） | `chore: 优化 .gitignore 忽略规则` |

**作用域**：可在类型后加括号细化（如 `fix(types):`、`docs(css):`），针对"同一类型多子系统"的场景。

## 提交纪律

1. **只提交相关文件**：不用 `git add -A` / `git add .`——个人仓库最易犯的错是把私人笔记、缓存、锁文件一起提交
2. **私人内容永不提交**：维护笔记目录、草稿等已被 `.gitignore` 隔离（见 [gitignore 策略](../02-config-spec/gitignore-spec.md)），提交前用 `git status` 确认边界
3. **提交前自检**：本地构建通过 + 无渲染问题（见[渲染铁律](../01-content-rules/render-rules.md)）

## 环境约束（实操层设计）

- PowerShell 不支持 bash heredoc：多行提交消息用**多个 `-m` 参数**（`git commit -m "标题" -m "正文"`）
- 提交消息中避免裸 `<` 字符（PowerShell 将其解释为重定向符）

## 与内容架构的关系

提交类型与仓库的三层内容结构对应：`feat` 对应新增章节/模块，`refactor` 对应章节重构（如按[页面结构标准](../01-content-rules/page-standard.md)对齐），`docs` 对应说明性更新。这让 `git log` 可以直接反映知识库的演进路径。
