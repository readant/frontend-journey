# 决策记录：现状 → 方案 → 选择 → 理由

> 本仓库已落地的工程决策汇总。每条统一格式：**现状 → 可选方案 → 最终选择 → 选择理由**。只收录已经落地、影响当前仓库形态的决策。

## D-01 三层内容架构

- **现状**：学习笔记数量增长后，单一目录将同时承载教学长文、速查短卡、实战案例，定位混乱
- **可选方案**：① 全部平铺在 `docs/` 下按语言域组织 ② 学习层 / 参考层 / 实战层三层分离 ③ 按"难度等级"组织
- **最终选择**：三层分离（学习层 `01-html/02-css/03-js` + 参考层 `3-reference/` + 实战层 `practices/`）
- **理由**：三种内容的消费方式不同——教学需要上下文推导，速查需要一句话直达，实战需要可运行代码；混在一起既拖慢速查检索又打断教学节奏。分层后每层职责单一，学习层通过 `::: tip 速查卡片` 链接参考层，保持内容单一来源

## D-02 每页闭环内容标准（七项评审标准）

- **现状**：早期章节写作无统一骨架，有的缺类比、有的缺练习，质量参差
- **可选方案**：① 不做标准，靠自觉 ② 仅对"复杂章节"做标准 ③ 全站统一"每页必须闭环"标准 + 逐章差距审查
- **最终选择**：以 `03-js/02-functions` 为样板落地七项标准（概念引入 / 符号解释 / 教学递进 / 辅助图示 / 前置铺垫 / 阶梯练习 / 速查链接），并建立 P1→P3 分阶段对齐路线图
- **理由**：个人知识库的"可读性"是最高资产；统一的页面骨架让任何章节的消费体验一致，也让审查（对照清单打 ✅/⚠️/❌）可机械执行。阶梯练习（10+8+5+3）与掌握目标保证"学完能自测"

## D-03 速查四要素 + 学习层不复制

- **现状**：速查内容曾在学习页内嵌，导致同一术语多处维护、版本漂移
- **可选方案**：① 保持内嵌 ② 全部移到参考层，学习层链接 ③ 参考层 + 学习层各留精简版
- **最终选择**：参考层手册术语统一四要素（**定义 / 语法示例 / 使用场景 / 注意事项**），学习层只通过 `::: tip 速查卡片` 链接，不复制
- **理由**：内容单一来源才能保证一致性；四要素固定了"速查表该写什么"，避免速查页变成罗列

## D-04 星盘双轨数据制

- **现状**：知识星盘需要兼顾"视觉展示"与"导航跳转"，单一数据源难以两全
- **可选方案**：① 单一数据文件同时含展示字段与 link ② 展示层（`star-map-data.ts` 52 节点）+ 链接层（`graph-data.json` 21 节点）分离
- **最终选择**：双轨数据制，展示层含 UI 属性（坐标/星级/助记），链接层仅核心节点 + `link` 指向手册
- **理由**：展示层数据量大且带视觉属性，导航层追求精简直达；两套数据各有消费者（渲染组件 / 未来导航功能）。代价是必须双写同步——已纳入[改动影响面](./01-content-rules/change-impact.md)契约

## D-05 思维导图 YAML 驱动 + 脚本生成

- **现状**：思维导图内容维护手改 markmap Markdown，格式易错、难统一
- **可选方案**：① 继续手改产物 ② 维护者只编辑 YAML，脚本生成产物 ③ 用可视化编辑器导出
- **最终选择**：`mindmap-data.yml` 为唯一编辑点，`npm run gen:mindmap` 脚本扫描模块目录 → 解析 YAML → 生成 `mindmap-content.md`
- **理由**：YAML 比 markmap Markdown 更贴近"数据"（字段化、可校验）；生成产物视为缓存、每次覆盖，杜绝手改漂移；输出确定性保证可重复构建

## D-06 渲染问题修复：`<strong>` 替代裸 `**` + 三步验证法

- **现状**：markdown-it 的 emphasis 侧翼规则使 `**X（Y）**`（加粗紧邻全角括号）渲染出裸 `**`，连续多个还交叉嵌套；单行/两行式 `:::` 容器永不闭合吞内容，且构建期不报错
- **可选方案**：① 修改 markdown-it 配置 ② 改写文本规避 ③ 改用 HTML `<strong>` + 建立结构化的渲染验证流程
- **最终选择**：内容层改用 `<strong>X（Y）</strong>`（VitePress 默认支持 raw HTML，显示不变）；验证层采用三步法——**整文件 markdown-it 渲染脚本检测裸 `**`（容器行置空 + 剔除代码块防误报）→ build 后 grep dist 产物 → 浏览器实测容器高度/层级**
- **理由**：不引入对解析器的 patch（与上游行为对抗、难维护）；`<strong>` 是纯展示语义，迁移成本低；三步验证让"静默渲染错误"变成可复现、可回归检查的流程

## D-07 base 前缀统一约定

- **现状**：GitHub Pages 按仓库名路由（`/frontend-journey/`），组件内硬编码链接曾漏加前缀导致 404
- **可选方案**：① 全部手写前缀 ② 依赖 VitePress 自动加 base ③ 约定分层处理：Markdown 链接自动加，raw HTML/组件链接必须用 `import.meta.env.BASE_URL`
- **最终选择**：分层约定（D-03 的兄弟约束），并列入[渲染铁律](./01-content-rules/render-rules.md)
- **理由**：Markdown 链接由 VitePress 构建期自动加 base；但 raw HTML 与 Vue 组件不经过该管线，必须显式拼接。统一规则避免"有的加有的不加"

## D-08 格式化契约：2 空格 + 双引号 + Markdown 特殊处理

- **现状**：项目曾用 tab 缩进，与主流前端仓库风格不一致；Markdown 行尾空格被编辑器清理破坏排版
- **可选方案**：① 保持 tab ② 全站迁移到 2 空格 + 双引号，`.md` 单独放宽 ③ 不引入格式化工具
- **最终选择**：`.prettierrc.cjs`（2 空格 / 双引号 / printWidth 100，`.md` 放宽到 120）+ `.editorconfig`（`.md` 段 `trim_trailing_whitespace = false`）协同
- **理由**：风格统一降低阅读摩擦；`.md` 特殊处理守护"行尾两空格 = 强制换行"的语法（见 [format-ts](./02-config-spec/format-ts.md)）

## D-09 GitHub Actions 版本锁定与依赖策略

- **现状**：部署工作流 actions 版本曾被误降级；CI 与本地依赖曾漂移
- **可选方案**：① 随用随升 ② 锁定已核实的官方最新版本 + CI 用 `npm ci`
- **最终选择**：actions 锁定 checkout@v5 / setup-node@v6 / configure-pages@v6 / upload-pages-artifact@v5 / deploy-pages@v5（升级前必须核实 GitHub 官方 releases 页）；CI 用 `npm ci` 按 lockfile 精确复现
- **理由**：版本漂移是个人维护最常见的隐性故障源；锁定 + 核实把部署从"玄学"变成"可审计"

## D-10 私人维护笔记与公开内容隔离

- **现状**：仓库既有公开学习内容，又有私人维护素材（碎碎念、临时待办、排障笔记）
- **可选方案**：① 全部入库 ② 私人内容写入 .gitignore 不提交，公开内容单独成章 ③ 分开仓库
- **最终选择**：`维护笔记/` 整体入 `.gitignore`；对外公开的工程实践经"迁移筛选"后输出到 `docs/maintenance-guide/`
- **理由**：公开仓库只保留"对读者有价值"的内容（架构、契约、schema、决策），私人素材与排障速查不构成读者价值；单仓库避免多仓库同步成本，靠忽略规则 + 筛选流程划清边界
